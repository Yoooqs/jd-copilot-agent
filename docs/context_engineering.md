# JD Copilot 上下文工程策略（Context Engineering）

## 一、 核心框架（Core Framework）
Context Engineering 不是简单的“文本压缩”，而是一个系统化的信息治理体系，包含四个核心环节：
1. **分层（Layout）**：规划什么信息常驻、什么信息动态注入、什么信息可遗忘。
2. **压缩（Compression）**：通过摘要生成等手段精简冗余信息，提升信息密度。
3. **调度（Scheduling）**：在什么时机（用户提问/循环触发）注入哪部分上下文，按需动态组装。
4. **预算控制（Budgeting）**：从全局视角限制单次请求的 Token 消耗上限，确保成本与性能的平衡。

---

## 二、 策略细则（Strategy Details）

### 2.1 分层策略（Layout）
- **第一层（永久常驻）**：系统提示词（工具定义 + Loop 规则 + Harness 护栏）。
- **第二层（变量注入）**：用户的简历（`resume_text`）。
- **第三层（动态检索）**：知识库召回的 Top K 个 JD 片段。
- **第四层（历史对话）**：最近 3 轮对话摘要（若超过 3 轮，截断旧记录）。

### 2.2 压缩策略（Compression）
- **简历压缩**：如果简历超过 1000 字，在注入变量前，先调用大模型将其压缩为 300 字的“核心经历摘要”。
- **历史对话摘要**：对话超过 5 轮后，启用“摘要记忆”，只保留关键结论，丢弃中间冗长的思考过程。

### 2.3 调度策略（Scheduling）
- **按需注入**：只有当用户的请求涉及“计算差距”或“改写简历”时，才触发 `resume_text` 的注入。
- **检索触发**：当用户询问特定公司/岗位要求时，才触发知识库检索（Top K=5）。
- **动态组装**：单次请求的上下文按“系统指令 > 变量 > 检索片段 > 历史对话”的优先级组装。

### 2.4 预算控制（Budgeting）
- **全局预算**：单次请求的上下文全局限制为不超过 4000 Tokens（作为后续优化目标）。
- **实际偏差**：当前实测由于 Agent Loop 的多轮推理和知识库检索，实际 Token 峰值在 9,000 左右，后续需通过更细粒度的裁剪迭代。

## 三、 实测数据与结论（A/B Test Results）

### 3.1 对照组设计
- **Test A（完整上下文）**：注入约 1500 字完整简历 + 连续对话历史。
- **Test B（压缩上下文）**：注入约 300 字精简简历 + 清空历史对话。

### 3.2 核心指标对比
| 指标 | Test A（完整上下文） | Test B（压缩上下文） | 变化 |
| :--- | :--- | :--- | :--- |
| **Token 消耗** | 29,372 | 9,376 | ⬇️ 降低约 68% |
| **响应延迟** | 169.24 秒 | 113.69 秒 | ⬇️ 降低约 33% |
| **输出质量评分** | 9 / 10 | 8.5 / 10 | ⬇️ 仅下降 0.5 分 |

### 3.3 结论与洞察
1. **降本增效显著**：压缩简历（300字）+ 限制记忆轮数后，Token 成本暴降 68%，延迟降低 33%，但质量评分仅下降 0.5 分。
2. **组件协同效应**：压缩导致模型初始评估分较低（6分），但得益于 Agent Loop 的自我修正机制，模型在信息不足时会主动进行更深入的结构化拆解（如细分 C2/C4 维度），有效弥补了信息缺失。
3. **未来迭代方向**：目前实际 Token 消耗（9,376）仍高于设定的全局预算（4000）。后续将引入更严格的“检索片段裁剪”和“历史对话滚动摘要”机制，进一步逼近 4000 Tokens 的目标。
