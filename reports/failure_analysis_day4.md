# Day 4 失败分析与产品迭代记录

## 一、 业务逻辑与模型表现类失败

### 1. 角色错位与专业幻觉 (q001, q002)
- **现象**：Baseline 在回答“Moonshot AI 看重什么能力”时，生成了“分布式训练、KV cache 压缩”等算法工程师的要求，完全脱离了“toB产品经理”的求职设定。在 q002 中，又输出了大量阿里云架构的宏观废话。
- **原因**：纯 LLM 缺乏具体的业务上下文约束，倾向于堆砌大词和预训练记忆。
- **迭代计划**：在 RAG 的提示词中强制加入“只允许使用明确标注公司名称（company）的片段”的防幻觉指令，严格锚定知识库。

### 2. 防幻觉机制与兜底测试 (q006)
- **现象**：面对不存在的“火星AI产品经理”JD，Baseline 毫无察觉，甚至试图编造该岗位的职责。RAG 则精准触发规则1，拒绝回答并引导提供真实资料。
- **原因**：RAG 的检索边界和提示词规则发挥了“安全阀”作用，证明了“知道自己不知道什么”在垂直业务中的极端重要性。
- **迭代计划**：将“安全与兜底”列入产品核心成功指标（KPI），保持 RAG 的拒答机制。

### 3. 多实体查询的语义漂移 (q002拆解)
- **现象**：对比“Moonshot AI 和阿里”时，Top 3 全被阿里占据。
- **原因**：向量检索一次只能关注一个焦点，多实体提问会导致“注意力分散”。
- **迭代计划**：确立“查询分解（Query Decomposition）”策略。在底层将“对比A和B”拆解为两个独立的单实体请求，各取 Top 3 再合并给大模型。

### 4. 生成型任务的检索锚定 (q005)
- **现象**：测试 q005（简历改写）时，发现如果不提供明确的 JD 公司锚点，检索系统无法准确召回“岗位职责”。
- **原因**：RAG 擅长“知识问答”，直接提问“帮我改写简历”容易导致检索机制失灵。
- **迭代计划**：在产品交互层设计“意图引导”，要求用户在提问时补充“基于 [目标公司] 的 JD 要求”，将生成任务强转化为检索任务。

## 二、 基础设施与系统稳定性类失败（面试核心加分项）

### 5. 额度耗尽、向量空间漂移与数据重建灾难
- **现象**：Dify 平台自带的 200 条免费额度耗尽，导致 LLM、Embedding、Rerank 链路全面瘫痪。随后在切换至开源模型时，更换 Embedding 模型导致旧数据向量失效，召回测试返回 0 结果。
- **原因**：AI 产品极度依赖外部 API，且不同 Embedding 模型的向量空间不兼容。Dify 在更换模型后未主动触发全量重算。
- **迭代计划（SOP确立）**：
  1. 确立“API 额度监控与多供应商降级方案”，将大模型、Embedding、Rerank 全部切换至自有 API Key（如硅基流动）。
  2. 确立“更换 Embedding 模型必须伴随全量数据重新索引”的技术纪律。果断执行“物理删库重建”策略，重新上传 `jd_clean.csv` 并强制系统重算向量。
