- 验证结果（工具测试数据）：

  2. 在成功调用的 5 条中，参数完全正确且无幻觉，有效工具调用的参数正确率为 100%（5/5）。
  3. 综合防御成功率：将“正确拒绝错误参数（如0周计划）”和“正确触发澄清（如未指明简历段落）”视作防御成功，Agent 的整体预期行为达成率为 10/10 = 100%。

- 卡点与排查过程（核心实战踩坑记录）：
  1. **参数幻觉：PRD 与提示词脱节导致模型凭空捏造简历**。在 `tools_spec.md` 中，`compute_gap` 明确要求输入 `resume_text`。但在 Dify 的 Agent 初始提示词中，我遗漏了对应的变量配置和上下文声明。模型为了强行输出合规的 JSON，凭空捏造了一份“3年经验AI产品经理”的假简历塞入参数。
     * **排查与修复**：定位到这是典型的“上下文依赖缺失”。立刻在 Agent 中增加 `resume_text` 变量，并在提示词中增加强制约束：“若缺失 `resume_text`，应拒绝调用，严禁编造参数”。
  2. **指令死锁：缺少后端执行导致模型卡在 JSON 输出阶段**。在测试 `generate_plan` 时，模型完美输出了 JSON 请求，但随后陷入停滞。
     * **排查与修复**：排查发现，系统提示词中设置了“必须且只能输出 JSON，等待后端返回结果”的强约束。由于我们采用的是“Prompt 模拟”架构，并没有真实的后端 API，模型“听话”地死等，导致了流程断链。后续通过输入“好的，请继续执行”来模拟后端返回，打破了死锁。这个卡点直接为 Day 6 引入 Agent Loop 提供了真实的架构优化依据。
  3. **上下文过长导致指令遗忘**：当输入包含简历、5个岗位和复杂提示词（35k Token）时，模型出现过头信息过载，只输出了 JSON 结构，却忘掉了“模拟执行结果”这一步。
     * **排查与修复**：在后续测试中，通过明确拆分步骤（“第一步输出JSON，第二步给出具体gaps列表”）并缩短单次请求的上下文，缓解了这一问题。

- 面试可讲点（核心话术准备）：
  1. **工具契约（Contract）设计**：我深刻认识到 Tool Use 不仅仅是让大模型“能调函数”，更要在 `tools_spec.md` 中严格定义“输入、输出、失败兜底”三段式。模型本身是概率性的，我们必须用结构化的约束去对抗它随意发挥的倾向。
  2. **意图消歧与结构化引导**：面对模糊的用户指令（如“突出 Builder 能力”），优秀的 AI 产品不是让模型去“猜”，而是提供结构化的选项（A/B/C）让用户选择。用确定性的交互取代不确定的模型推断，是建立用户信任的关键。
  3. **防幻觉与诚实边界**：在执行简历改写（rewrite_resume_bullet）时，我设定了严格的“真实性约束”。Agent 没有迎合 JD 堆砌虚构经验，而是主动输出了“诚实边界声明”，拒绝将我包装成搭建过生产级 RAG 系统的工程师，并提供了应对面试官追问的真实话术。这证明了：**在企业级产品中，工具的“防幻觉机制”比“生成能力”更宝贵。能对用户说‘不’，才是建立信任的开始。**
  4. **大模型与后端的职责边界**：通过“指令死锁”的卡点，我彻底理解了系统架构的本质——大模型只负责“决策（决定调什么工具、传什么参数）”，真正精确的“执行计算”必须由后端代码来完成。这也为 Day 6 引入 Agent Loop 奠定了架构认知基础。
